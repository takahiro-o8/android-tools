# 全アプリ共通のバージョン方針（2026-11-16）

ユーザーの最新指示により、正式APKの表示バージョンは数字3要素の`x.y.z`だけにする。ビルド番号、`.bN`、日付、その他の接尾辞を付けない。既存6アプリ（Launcher、Limitless、File、LinkAutoDL、G-widget、Voice Memory）と今後の新規アプリに共通。

## 採番

- `version.properties`の`VERSION_NAME`は`x.y.z`の基準・下限。公開済みAPKの最大バージョンより大きければ指定値を採用する。
- 指定値が公開済み最大値以下なら、最大値のパッチ番号`z`を1つ増やす。例: `1.4.0` → `1.4.1` → `1.4.2`。マイナー・メジャー更新は基準値を明示して行う。
- 比較は3整数の組として行う。`2.10.0 > 2.9.0`。文字列順、タグ名、Releaseタイトル、公開日時、GitHub Actionsの実行番号から判定しない。
- 移行時の旧`x.y.z.bN`は`x.y.z`として比較する。旧`1.4.0.b11`の次は`1.4.1`。履歴を読み取る場合だけ旧形式を許容し、新規APKでは拒否する。
- Androidが上書き更新判定に使う`versionCode`は必要な内部整数。`max(VERSION_CODEの下限, 公開済みAPKの最大versionCode + 1)`で決め、GitHubのビルド番号を使わない。既存の大きな値（例100173）も維持して次を100174にする。
- 初回は基準値を採用。失敗・キャンセル・公開済みと同じ入力のスキップでは番号を消費しない。再試行は公開済み履歴が変わらない限り同じ候補になる。

## 根拠と公開前検査

`next-release-version.py`と`verify-release-lineage.py`は`release_versions.py`を共用する。正式Releaseの検証済み`Verified-APK`メタデータを読み、未記録の旧版だけAPK実体を取得する。アプリID・版数を取得できない場合は失敗として公開を停止する。

採番後に署名付きAPKを作り、公開直前に履歴を再取得する。APK実体のアプリID・versionCode・versionNameを候補と照合し、保持されている全正式APKより**表示名と内部番号の両方が厳密に大きい**場合だけ公開する。固定署名・直列公開・最新3件保持も維持する。

APK名は`AppName-x.y.z.apk`、Release名は`AppName x.y.z`、タグは`vx.y.z`。過去のRelease・APK名は変更しない。

## 今回の反映と資源節約

今回の基盤・参照SHA変更は`[skip ci]`コミットで反映し、Actions・APKビルド・新規Releaseを起動しない。各アプリは新基盤の固定SHAを取得する設定へ更新し、次回の通常ビルドから適用する。恒久的なCI停止や署名鍵の変更はしない。

採番・移行・数値順・不正形式・公開競合・整数上限・履歴検証のローカルチェック:

```sh
python3 -m unittest discover -s scripts/tests -v
bash -n actions/build/build.sh
```

Androidビルド、E2E、エミュレーター、GitHub通信を伴うテストではない。新方式のAPK実体の検証は次回の通常ビルドで共通Actionが行う。
